# 우리동네 소식

> 동네 사람들이 유용한 생활 정보를 게시글로 공유할 수 있는 지역 커뮤니티 서비스

## 📌 프로젝트 소개

**우리동네 소식**은 지역 주민들이 자신이 사는 동네의 맛집, 카페, 행사, 생활정보 등을 게시글로 공유하고 서로 소통할 수 있는 지역 커뮤니티 서비스입니다.

여러 SNS나 검색 서비스를 돌아다니지 않고도 실제 동네 주민들이 공유한 생활 정보를 한곳에서 확인할 수 있도록 만드는 것을 목표로 합니다.

---

## 🎯 프로젝트 목표

- 동네 생활 정보를 한곳에서 쉽게 확인할 수 있도록 한다.
- 지역 주민이 직접 정보를 작성하고 공유할 수 있도록 한다.
- 게시글 작성부터 조회, 수정, 삭제, 댓글, 좋아요까지 연결되는 사용자 흐름을 구현한다.
- Next.js와 MongoDB를 활용하여 화면 ↔ API ↔ DB가 연결되는 Full-stack 서비스를 구현한다.
- Figma를 기반으로 설계한 UI를 실제 서비스로 구현하여 UI 디자인 및 프로토타이핑 역량을 보여준다.

---

## 👥 주요 사용자

자신이 사는 동네의 맛집, 카페, 행사, 생활정보 등을 찾고 다른 사람들과 공유하고 싶은 지역 주민

## ❓ 사용자가 겪는 문제

동네의 맛집이나 행사, 생활 정보 등을 찾으려면 여러 SNS나 검색 서비스를 돌아다녀야 하며, 실제 동네 주민의 생생한 정보를 한곳에서 찾기 어렵습니다.

### 💡 해결 방법

지역을 기반으로 게시글을 모아 사용자가 필요한 동네 정보를 쉽게 찾고, 직접 경험한 정보를 게시글로 공유할 수 있도록 합니다.

## 🖥️ 주요 화면

### 1. 회원가입 화면

사용자가 아이디, 비밀번호 등의 정보를 입력하여 서비스에 회원가입합니다.

### 2. 로그인 화면

가입한 사용자가 아이디와 비밀번호를 입력하여 로그인하고 서비스를 이용합니다.

### 3. 게시글 목록 화면

동네 주민들이 작성한 게시글을 목록으로 확인하고 검색 및 카테고리별로 원하는 게시글을 찾습니다.

**화면에 표시되는 정보**
- 게시글 제목
- 작성자
- 작성 시간
- 카테고리
- 게시글 사진
- 좋아요 수
- 댓글 수

### 4. 게시글 작성 화면

사용자가 제목, 내용, 사진, 카테고리를 입력하여 동네 생활정보 게시글을 작성합니다.

### 5. 게시글 상세 화면

선택한 게시글의 제목, 작성자, 작성 시간, 내용, 사진, 좋아요 수와 댓글을 확인하고 좋아요 및 댓글을 작성합니다.

### 6. 게시글 수정 화면

게시글 작성자가 기존 게시글의 제목, 내용, 사진, 카테고리 등을 수정합니다.

### 7. 댓글 관리 화면

게시글에 작성된 댓글을 확인하고 사용자가 작성한 댓글을 삭제합니다.

### 8. 검색 결과 화면

검색어와 카테고리를 기준으로 관련 게시글을 확인하고 원하는 게시글의 상세 내용을 확인합니다.

### 추가 화면

- 인기 게시글 화면
- 사용자 프로필 화면
- 북마크 화면
- 게시글 신고 화면

## 🗄️ Database 설계

### 주요 Collection

MVP에서는 다음 4개의 Collection을 우선 사용합니다.

- `User`
- `Post`
- `Comment`
- `Like`

추가 기능 구현 시 다음 Collection을 고려합니다.

- `Bookmark`
- `Report`

### Post Schema

| Field | Type | 설명 |
|---|---|---|
| `title` | String | 게시글 제목 |
| `content` | String | 게시글 내용 |
| `authorId` | ObjectId | 게시글 작성자 |
| `category` | String | 게시글 카테고리 |
| `createdAt` | Date | 게시글 작성 시간 |
| `updatedAt` | Date | 게시글 수정 시간 |
| `imageUrl` | String | 게시글 사진 저장 위치 |
| `likeCount` | Number | 좋아요 개수 |

### Comment Schema 주요 Field

| Field | Type | 설명 |
|---|---|---|
| `postId` | ObjectId | 댓글이 작성된 게시글 |
| `authorId` | ObjectId | 댓글 작성자 |
| `content` | String | 댓글 내용 |
| `createdAt` | Date | 댓글 작성 시간 |

### Like Schema 주요 Field

| Field | Type | 설명 |
|---|---|---|
| `postId` | ObjectId | 좋아요 대상 게시글 |
| `userId` | ObjectId | 좋아요를 누른 사용자 |
| `createdAt` | Date | 좋아요 생성 시간 |

## 🔗 Collection 관계

### User ↔ Post

**1 : N 관계**

한 명의 사용자는 여러 개의 게시글을 작성할 수 있고, 하나의 게시글은 한 명의 작성자와 연결됩니다.

```text
User (1)
   │
   └──────────< Post (N)
                 authorId
```

### Post ↔ Comment

**1 : N 관계**

하나의 게시글에는 여러 개의 댓글이 작성될 수 있습니다.

```text
Post (1)
   │
   └──────────< Comment (N)
                 postId
```

### User ↔ Post

**N : N 관계**

사용자는 여러 게시글에 좋아요를 누를 수 있고, 하나의 게시글에도 여러 사용자가 좋아요를 누를 수 있습니다.

이 관계는 `Like` Collection을 통해 연결합니다.

```text
User (N)
   │
   └──── Like ──── Post (N)
       userId       postId
```

## ✍️ 게시글 작성 API

### Request

`POST /api/posts`

```json
{
  "title": "우리 동네 맛집 추천",
  "content": "근처에 새로 생긴 맛집을 추천합니다.",
  "category": "맛집"
}
```

`authorId`는 클라이언트가 직접 보내지 않고 서버에서 로그인한 사용자의 인증 정보를 확인하여 처리합니다.

### 성공 Response

**HTTP 201 Created**

```json
{
  "id": "게시글 ID",
  "title": "우리 동네 맛집 추천",
  "content": "근처에 새로 생긴 맛집을 추천합니다.",
  "authorId": "작성자 ID",
  "createdAt": "작성 시간"
}
```

## 🔐 인증 및 권한

### 로그인 없이 사용할 수 있는 API

- `GET /api/posts`
- `GET /api/posts/:id`
- `GET /api/comments/:postId`

### 로그인이 필요한 API

- 게시글 작성
- 게시글 수정
- 게시글 삭제
- 댓글 작성
- 댓글 삭제
- 좋아요

### 권한 검사가 중요한 기능

게시글 수정 및 삭제가 가장 중요합니다.

로그인 여부만 확인하는 것이 아니라 현재 로그인한 사용자의 ID와 게시글의 `authorId`가 일치하는지 확인해야 합니다.

```text
로그인 사용자 ID
       ↓
게시글 authorId와 비교
       ↓
일치 → 수정 / 삭제 허용
불일치 → 권한 없음
```

이를 통해 다른 사용자가 자신의 게시글이 아닌 게시글을 수정하거나 삭제하는 것을 방지합니다.

## ✅ Validation

### Client에서 확인할 것

1. 제목과 내용이 비어 있는지 확인
2. 제목과 내용의 글자 수가 제한을 초과하지 않는지 확인
3. 공백만 입력된 경우 확인

### Server에서 반드시 확인할 것

1. 로그인한 사용자인지 확인
2. 제목, 내용, 카테고리 등 필수 값이 전달되었는지 확인
3. 전달된 데이터의 형식과 값이 올바른지 확인
4. 게시글 수정 / 삭제 시 작성자 권한 확인

### Model / DB에서 보장할 것

1. `authorId`, `postId`, `userId`가 올바른 ObjectId 관계를 가지도록 관리
2. 필수 데이터가 없는 잘못된 데이터가 저장되지 않도록 관리

## 🧪 테스트 시나리오

### 정상 케이스

로그인한 사용자가 제목, 내용, 카테고리를 모두 입력하고 게시글을 등록합니다.

**예상 결과**

- Post Collection에 게시글이 정상적으로 저장됩니다.
- `201 Created` 응답을 받습니다.
- 게시글 상세 화면으로 이동합니다.

### 실패 케이스

로그인하지 않은 사용자가 게시글 등록을 시도합니다.

**예상 결과**

- 게시글을 저장하지 않습니다.
- `401 Unauthorized` 응답을 반환합니다.

### 경계 케이스

게시글 제목이나 내용이 허용된 최대 글자 수와 정확히 같은 경우를 테스트합니다.

**예상 결과**

허용된 최대 글자 수이므로 정상적으로 게시글이 등록됩니다.

### 놓치기 쉬운 케이스

제목이나 내용에 공백만 입력하는 경우입니다.

**예상 결과**

입력을 유효하지 않은 값으로 판단하여 게시글을 등록하지 않습니다.

## 🐛 디버깅 전략

### 예상 문제

게시글 등록 버튼을 눌렀는데 데이터가 DB에 저장되지 않는 경우

### 확인 순서

1. Client에서 `POST /api/posts` 요청이 정상적으로 전송되었는지 확인
2. Server에서 Request 데이터가 정상적으로 들어왔는지 확인
3. 로그인 인증과 `authorId`가 정상적으로 확인되는지 확인
4. MongoDB의 `Post` Collection에 데이터가 실제로 저장되었는지 확인

### 로그로 확인하면 좋은 값

- `title`
- `content`
- `category`
- `authorId`
- API 요청 URL
- HTTP 상태 코드
- DB 저장 결과

---

## ⚠️ 설계 과정에서 발견한 문제

API 명세를 작성하면서 ERD와 API에서 `authorId`를 처리하는 방식이 명확하지 않았던 문제를 발견했습니다.

### 수정한 내용

클라이언트가 `authorId`를 직접 보내지 않고, 서버에서 로그인한 사용자의 인증 정보를 확인하여 `authorId`를 Post에 저장하도록 수정했습니다.

또한 게시글 수정 API를 위해 Post Schema에 `updatedAt`을 추가했습니다.

### 수정 이유

API와 DB의 역할을 명확하게 분리하고, 로그인한 사용자와 게시글을 정확하게 연결하기 위해 수정했습니다.
